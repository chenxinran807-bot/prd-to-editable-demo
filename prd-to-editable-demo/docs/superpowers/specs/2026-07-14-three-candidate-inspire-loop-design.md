# Three-Candidate Inspire Loop Design

## Goal

让产品经理在外部 Agent 中只提交一份 PRD，即可自动获得三个可交互的 Inspire 高保真候选框架；三个候选覆盖同一组需求、状态与主流程，用户选中一个后，以其 `assetId` 作为唯一父版本继续手动或自然语言迭代。

## Product Promise

专业模式的成功终态不是交接包，也不是退出码，而是三个真实可访问的 Inspire 候选资产以及一份可解释的比较结果。只有快速评审模式才允许直接交付本地 HTML。

“高保真”声明必须同时满足：找到合格业务设计 Skill、真实激活该 Skill、生成真实 Inspire 预览、通过需求覆盖审查，并保留主观视觉验收状态。缺少合格设计能力时，系统阻塞高保真声明，不静默降级。

## User Experience

1. 用户在 Aime、Codex 等外部 Agent 中提交 PRD，可选附加截图、Figma、素材或意图。
2. Agent 生成带原文证据的统一需求模型，包括页面、业务对象、动作、状态、流转、推断和缺口。
3. 统一入口查询当前账号在 Inspire 中可见的业务设计 Skill，并选择唯一高置信候选。
4. 系统基于同一需求模型、同一设计 Skill 和同一验收契约生成三个结构与视觉方向不同的候选。
5. 三个候选分别进入 Inspire 私有收纳箱，拥有独立 `assetId`、预览链接、截图和审查报告。
6. 外部 Agent 展示 A/B/C 对比卡片。支持浏览器比较页时展示缩略图和选择控件；不支持时返回三个编号预览链接。
7. 用户选择一个候选。系统记录选择理由和被选 `assetId`，将其晋升为唯一已接受版本。
8. 后续 Agent 修改使用该 `assetId` 作为 `--ref`；用户也可直接在 Inspire 中手动编辑并保留撤销。未选方案保留为探索记录，但不进入正式版本链。

## Candidate Contract

三个候选必须保持以下内容完全一致：

- 用户角色与目标
- 业务对象与必要文案语义
- 必须覆盖的页面或功能单元
- 用户动作、状态、分支和主流程终点
- 业务设计 Skill、品牌资产来源及质量门禁
- 可编辑维度要求

允许变化的内容：

- 页面信息架构与内容分组
- 主次操作的位置与层级
- 导航、Tab、卡片、弹层或分步流程等交互框架
- 在业务设计系统允许范围内的视觉层级与组件组合

禁止为了制造差异而删除需求、虚构业务流程、切换业务设计系统、改变核心成功标准或使用无来源素材。

需求模型还必须生成一组冻结任务。每个任务包含入口、只允许通过当前 UI 完成的动作序列、可观察终态和失败条件。页面存在、URL 改变或截图成功不能替代任务终态；例如分类切换必须同时证明内容变化，交互控件必须产生可观察反馈。

三个方向不写死具体业务名称。系统根据需求形态生成可解释的方向标签，例如效率优先、内容沉浸或转化聚焦；标签必须由当前 PRD 推导，不能作为固定模板硬套。

## Architecture

### 1. Semantic Requirements

现有 `model-semantic` 继续作为事实源。统一入口必须先验证原文证据，再进入专业生成。确定性解析只能作为低置信兜底；专业模式缺少页面或流转时继续使用 `requirements-blocker.json` 阻塞。

### 2. Acceptance Contract

新增从语义需求到 `auditRequirements` 的纯函数转换，至少输出：

- `actions`
- `components`
- `states`
- `touchLabels`
- `editableDimensions`
- `screens`
- `transitions`

真实 CLI 生成的交接包必须包含该契约。测试不得再手工构造一份生产链路不会生成的 `auditRequirements`。

### 3. Business Skill Registry

将 `skills visible` 的自然语言元数据规范化为统一候选结构：

- `source`、`skillKey`、`version`、`packageHash`
- `domains`、`products`、`platforms`、`surfaces`
- `capabilities`、`exclusions`
- `qualityLevel`
- `intentKeywords`

匹配顺序为业务产品、用户类型、平台/端、页面域、能力覆盖、版本与来源策略。`built-in`、`public`、`workspace` 默认可参与自动匹配；`private` 只有在用户显式指定，或进入 owner 确认的允许名单时参与。

只有第一名达到最低分且与第二名保持足够差距时自动选择。否则返回 2–3 个候选及匹配依据，让用户选择。禁止猜第一个。

### 4. Three-Candidate Generation

统一入口直接编排 Inspire，不再把 `specialist-handoff.json` 当作用户终态。它仍可作为内部检查点保存。

系统从需求模型生成三个 `candidateBrief`。每个 Brief 记录：

- 稳定需求契约
- 本方案允许变化的结构策略
- 本方案的视觉层级策略
- 禁止改变的业务约束
- 候选编号和可解释标签

三个候选使用相同的业务设计 Skill 精确版本。每次生成都校验 `skillTrace.activatedSkills` 和 `openedSkills`，确保没有退化为 `mobile-shell` 或其他 built-in fallback。

输入素材按角色分阶段处理。结构与方案素材优先用于建立候选父资产；竞品、现状和风格参考只能基于父资产通过 `--ref` 做定向优化。每阶段最多遵守 Inspire 当前文件上限，并保存素材角色、文件哈希、父资产、子资产、命令参数和 Skill trace。禁止为了绕过数量限制把不同角色素材无差别塞入一次生成。

候选生成允许部分失败，但不得伪装成三个成功方案：

- 三个成功：进入比较。
- 两个成功：展示两个并标记第三个失败，可重试失败项。
- 少于两个成功：保持阻塞并返回可重试原因，不进入选择。

### 5. Comparison And Selection

生成 `candidate-comparison.json`，包含候选资产、截图、结构差异、推断点、审查结果和选择状态。

浏览器比较页仅是选择器，不是最终原型容器。它读取比较数据，展示三个候选的缩略图、定位、关键差异和 Inspire 预览入口。选择动作写入 `selected-candidate.json`。

不支持浏览器时，外部 Agent 使用同一比较数据返回 A/B/C 链接，并将用户文本选择写入相同选择文件。

选择必须是显式动作。未经用户选择，不自动把任何候选设为已接受版本。

### 6. Version Lineage

选择后，被选候选成为 `currentAssetId`。另外两个候选标记为 `not-selected`，保留但不得成为后续修改父版本。

后续自动修改始终基于当前已接受 `assetId` 创建候选版本；审查失败时保留上一已接受版本。手动编辑仍在 Inspire 中完成。

## Quality Gates

每个候选至少通过：

- 指定业务设计 Skill 真实激活并打开
- PRD 必要页面、动作、状态和流转覆盖
- 主流程能从入口到结果
- 图片、Icon、位置、大小、文字、颜色、显隐、状态和跳转具备可编辑声明
- 无 Emoji、文字图标、通用紫色渐变、桌面导航和假手机框
- 外部资产和图标具备来源记录
- 冻结任务必须从真实入口通过链式点击完成，不得直接跳转目标 URL 冒充成功
- 点击必须产生可观察的内容、状态或视觉变化，只有 URL 变化不算完成
- 所有可操作控件具备可定位语义，协议勾选、切换、相机翻转等控件必须真实改变状态
- 图片自然尺寸不得为 0；未批准外链请求、失败请求和中止请求必须为 0
- 移动端目标视口不得出现元素越界、不可预期重叠或横向溢出

确定性规则通过后仍标记 `subjectiveReview: required`。只有拿到真实截图并完成同视口视觉审查后，才可声明达到业务原生高保真。

## Evaluation

基准测试必须从“交接成功”升级为“真实候选完成”。正式电商案例至少覆盖商品发现、交易结算和售后服务，并验证：

- 三个真实 Inspire `assetId`
- 三个可访问预览和截图
- 同一需求契约与同一设计 Skill
- 三种可辨识但不改变业务事实的框架
- 所有候选通过动作、状态和主流程审查
- 用户选择后只有一个父版本进入迭代
- 每个候选的冻结任务逐项通过率及原始浏览器记录
- 图片完整性、网络失败、控制台错误、元素越界和控件语义检查

模拟 CLI 只用于单元和失败测试，不能作为端到端高保真成功证据。

## Experiment Evidence Incorporated

2026-07-14 新实验显示，现有 `prd-to-editable-demo` 在穿搭场景中虽达到 15/15 captures、零编译和运行错误，但冻结任务仅通过 2/5；分类切换只改变 URL、引导信息缺失、AI 入口无法到达。相机场景浏览器 QA 为 10/12，并出现协议控件语义不足、翻转无反馈、32 张缩略图中 24 张自然尺寸为 0，以及大量失败或中止的外链请求。

因此本设计把冻结任务链式点击、可观察状态变化、图片与网络稳定性和分阶段素材策略设为 P0。自动截图数量、页面数量和静态结构校验只能作为辅助证据，不能决定候选是否有效。

## Error Handling

- 未登录或网络失败：保存语义需求和进度，返回恢复动作。
- 无匹配业务设计 Skill：阻塞高保真声明并给出安装、共享或选择建议。
- 多个同等候选：请求用户选择，不自动猜测。
- Skill 未真实激活：候选失败，不交付该资产。
- Inspire 未返回可审查结构：候选保持 `needs-review`，不得自动晋升。
- 少于两个有效候选：不进入比较，支持幂等重试。
- 用户未选择：三个候选均保持探索状态。

## Scope

本阶段包含统一入口、自动匹配、验收契约、三候选生成、比较数据、显式选择和版本继承。

本阶段不包含：自动发布新的业务设计 Skill、替代 Inspire 的本地专业编辑器、无需视觉证据的像素级承诺，以及对所有外部 Agent UI 的定制实现。

## Acceptance Criteria

1. 产品经理只需向外部 Agent 提交 PRD；除登录、授权或候选歧义外，无需理解命令、退出码或交接包。
2. 专业路径的成功结果至少包含两个、目标为三个真实 Inspire 候选，而不是只生成交接文件。
3. 每个候选共享同一需求和验收契约，并使用同一业务设计 Skill 精确版本。
4. 真实交接包自动包含 `auditRequirements`，缺失任一必要动作或状态时候选不能通过。
5. 多 Skill 歧义时系统返回候选及依据；唯一高置信候选时自动运行。
6. 用户显式选择后，只有选中 `assetId` 成为后续迭代父版本。
7. 端到端成功声明必须有真实 Inspire 预览、截图和审查证据；模拟测试不计入该声明。
