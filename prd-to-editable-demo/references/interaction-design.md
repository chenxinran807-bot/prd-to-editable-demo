# 交互设计协议

## 从任务推导界面

- 先确定角色要完成的任务、业务对象、动作、规则和状态，再推导界面；不得把 PRD 章节直接变成页面。
- 每个界面只有一个清晰职责。页面、弹窗、浮层或抽屉的选择由任务连续性和上下文保持需求决定。
- 每条主流程必须有入口、推进动作、系统反馈、结果和返回路径，不允许断头跳转。
- 交互描述使用“触发条件 → 系统行为 → 用户反馈”，并关联需求证据或明确标记为推断。

## 状态与组件

- 对适用组件检查 `default`、`loading`、`empty`、`error`、`disabled`、`permission` 和 `success` 状态；不适用的状态说明原因，不机械添加页面。
- 表单包含输入约束、实时或提交校验、提交中、成功和失败反馈；列表包含加载、空、错误和刷新路径。
- 禁止弹窗套弹窗。复杂分支改为页面、抽屉或同层状态切换。
- 同一区域区分主要、次要和文本动作；破坏性动作必须二次确认并提供明确结果。

## 可编辑与可追溯

- 每个可编辑节点使用稳定且唯一的 key，版本迭代时优先保持 key 不变。
- 文字、颜色、图片、Icon、位置、大小、显隐、禁用状态和跳转目标必须有明确绑定。
- 页面和流转能追溯到 `model-semantic` 需求结构；缺少原文支持的界面命名、状态和规则进入 assumptions 或 gaps。
